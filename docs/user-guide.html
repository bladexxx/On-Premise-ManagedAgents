1. Scope and positioning

This guide describes only the enterprise on-premise edition of OMA. In this document, “server” means apps/main-node and “frontend” means OMA Console. Managed-platform-only Workers, Durable Objects, D1, R2 and hosted billing flows are outside the scope of this guide.

For business users

Select a Workspace, create or use an Agent, send tasks, and review progress and outputs without needing to understand databases or containers.

For analysts

Upload files, mount Memory Stores, configure models and environments, and review work through Session events and outputs.

For developers

Use REST APIs, SSE, SDKs, API Keys and CLI tokens to integrate OMA with internal systems and automation.

For administrators

Operate authentication, Workspaces, member roles, model credentials, runtimes, sandboxes, backups and multi-instance deployments.

2. Quick start

2.1 First use for ordinary users

  1. Open the OMA Console URL provided by the administrator.
  2. Sign in with an account enabled by the administrator. Authentication is provided by better-auth; deployments can enable email/password, OTP and configured OIDC SSO.
  3. Use the top Workspace switcher to select an existing Workspace or create a new one.
  4. Go to Agents and create an Agent. At minimum, provide a name, model and system prompt.
  5. Create a Session, select the Agent, Environment and optional resources, then send the first task.
  6. In Session detail, review live events, Agent replies, tool calls, model calls and output files.
Recommended first exerciseCreate a read-only analysis Agent, mount a test file, and ask it to “summarize the file and list key metrics” in a controlled Environment. Learn Session, event stream and output download first, then connect external resources.

3. Workspace, Tenant and permissions

A Workspace is the work area users see in Console; the server implements it as a Tenant. It is not just a UI label, but the root boundary for resource and request isolation.

3.1 User and Workspace relationship

ConceptMeaningTypical relationship
UserLogin identityOne User can join multiple Workspaces.
Workspace / TenantResource isolation domainOne Workspace can contain multiple Users.
MembershipAssociation record between a User and WorkspaceThe same User can hold different roles in different Workspaces.
tenant_idServer-side data isolation keyUsually corresponds to a Workspace ID; API calls must run in the correct active tenant context.

3.2 Roles

RoleAllowed actionsLimits
ownerManage Workspace members, grant or revoke owner, and manage resources inside the Workspace.Cannot remove the last owner.
adminAdd, modify and remove ordinary members; manage day-to-day Workspace resources.Cannot grant or revoke owner.
memberUse visible Workspace resources and create/run tasks.Cannot manage members.
Important permission boundaryThe current code implements Workspace membership and role checks, but roles are not further decomposed into a per-resource can_read, can_create, can_update, can_delete permission matrix. Treat Workspace as the primary resource boundary and grant API Keys carefully.

3.3 Console and API entry points

  • Workspace list: GET /v1/me/tenants
  • Create Workspace: POST /v1/tenants
  • Current user: GET /v1/me
  • List members: GET /v1/tenants/:tenantId/members
  • Add member: POST /v1/tenants/:tenantId/members
  • Change role: PATCH /v1/tenants/:tenantId/members/:userId
  • Remove member: DELETE /v1/tenants/:tenantId/members/:userId

Member addition requires an existing user account in this OMA instance. Administrators can optionally set the system-wide OMA_ALLOWED_EMAIL_DOMAINS configuration to restrict which email domains may sign in through OIDC or be added to Workspaces. If SSO succeeds but the local user record has not been synchronized, “User account not found” can still appear.

4. Organization Settings and organization defaults

Organization Settings sit above Workspaces and define shared defaults for models, execution configuration, allowed Harnesses and security policies. They are not ordinary resources of a single Workspace.

The Console currently registers the following pages, although they may not always appear in the regular sidebar:

  • Organization Settings: /organization
  • Organization Workspaces: /organization/workspaces

If the sidebar does not show an entry, access these routes directly or ask an administrator to expose internal navigation links. The pages read GET /v1/oma/org/defaults and GET /v1/oma/org/workspaces.

4.3 Effective Workspace settings

A Workspace can inspect its final effective configuration through GET /v1/oma/org/effective-settings. Returned values distinguish their sources:

  • workspace: the Workspace configured its own model or execution environment and has higher priority.
  • org_default: the Workspace lacks its own setting and inherits the organization default.
  • org_policy: allowed Harness list, BYOK, dedicated environment and networking policy come from organization policy.
  • missing: no usable default exists and an administrator must fill it in.

If the organization configures a default execution profile, POST /v1/oma/org/apply-org-defaults can materialize it as the Workspace default Environment. Availability depends on whether the current deployment provides the corresponding application service.

5. Agent, Harness and ACP Proxy

An Agent is a reusable “how to work” configuration, not one execution. A Harness is the Agent execution engine. ACP Proxy is a special execution mode that delegates the Agent loop to a connected local ACP runtime.

5.1 Harness Catalog

The Console /harnesses page is the Harness Catalog. It reads the deployed manifest from GET /v1/harnesses and shows name, status, provider, version, installed/enabled state, capability support, native tools, compatibility and OMA tools.

HarnessPositioningBest fitStatus
Default OMAStandard OMA agent loopGeneral business Agents, tool calls, file and Memory operationsstable
StrandsAgent loop backed by Strands AgentsAgents that need Strands execution semanticsbeta
Deep AgentsAdvanced loop with planning, skills and synchronous sub-Agent delegationComplex analysis, task decomposition, multi-step planningbeta
ACP ProxyDelegates to a registered local ACP runtimeRunning Claude, Codex, OpenClaw or other ACP-compatible Agents on a user/team machineexperimental

The Catalog manifest is what the current deployment actually registered. If a harness is not installed, disabled or incompatible, do not select it based on name alone.

5.2 How to choose a Harness

NeedPreferReason
Standard OMA workflow running in an OMA-managed sandboxDefault OMAThe most stable compatibility surface and the safest default starting point.
Use the Strands execution modelStrandsUses a Strands-backed loop. It is beta, so run regression checks first.
Native planning, write_todos and task sub-Agent toolsDeep AgentsConsole exposes native tools and tool configuration; suitable for complex work.
Call a local Claude/Codex/other ACP Agent installed on a machineACP ProxyExecution occurs on the Local Runtime-bound machine and does not use an OMA isolated sandbox.
Selection principleChoose by “execution location” first, then by “Agent capability”: choose Default/Strands/Deep Agents when you need an OMA-managed isolated environment; choose ACP Proxy when you need a local ACP Agent. Do not treat ACP Proxy as a normal sandbox harness.

5.3 Harness configuration when creating an Agent

Select the Harness in the Agent create/edit dialog. Ordinary harnesses are saved as Agent _oma.harness and optional _oma.harness_config. Deep Agents can configure tool switches. ACP Proxy also requires runtime binding, including runtime_id and acp_agent_id. If ACP Proxy only has a partial binding, the current implementation falls back to ordinary OMA loop semantics; confirm both fields are configured.

The Business Agent creation flow can turn a business description into a draft. Review the Agent name, model, system prompt, tools and resource bindings before saving. 7. Resources management

7.1 Environment

Environment defines sandbox dependencies and networking policy. It can configure Python, npm, apt, cargo, gem and Go packages plus networking rules. After creation, it can be selected by Sessions. Built-in environments can be initialized through bootstrap entry points.

POST /v1/environments GET /v1/environments GET /v1/environments/:id POST /v1/environments/:id/archive

7.2 Files

Files are used to upload input files and store reusable file metadata. Sessions can mount files into sandbox paths. Production deployments must back up both database metadata and the actual blob content.

7.3 Memory Stores

A Memory Store is persistent memory across Sessions. Memory is organized by path and supports list, read, create, update, delete, version history, CAS conditional writes and historical version redact. Console provides Memory Store list, detail, content editing and version operations.

  • Recommended paths: /preferences/formatting.md, /projects/project-a/notes.md.
  • Use precondition: not_exists to prevent first-create overwrite.
  • Use content_sha256 for concurrent write protection.
  • Redacting a version removes sensitive content while preserving the audit row; the current live head cannot be redacted directly.
  • Mount through Session resources at /mnt/memory/<store_name>/.

7.4 Credential Vaults

Vault stores credentials such as MCP OAuth, static Bearer tokens and command secrets. The design goal is that credentials do not enter the Agent sandbox; the outbound proxy injects them after matching URL or command. Vaults and Credentials belong to the current Workspace.

POST /v1/vaults GET /v1/vaults POST /v1/vaults/:id/credentials POST /v1/vaults/:id/archive

Security requirementDo not put API tokens, passwords or OAuth refresh tokens into Agent system prompts, Skill files, Memory or ordinary Files. Use Vault instead, and revoke credentials that are no longer needed after testing.

7.5 Skills and MCP

Skills are reusable prompt fragments and files, supporting upload, list, version and delete. MCP entry points support connection probing and credential matching. Skills fit stable domain knowledge; Memory fits persistent information that changes with tasks; Vault fits secrets.

7.6 Resource visibility and access review

Resources can be private to their creator or visible within the Workspace according to the current access policy. Console provides a workspace access inventory and highlights resources requiring review. Members can create private Agents, Skills and Memory Stores when permitted; owners and admins manage the Workspace-level visibility and permissions policy.

8. Models, Model Cards and runtimes

8.1 Model Card

A Model Card binds provider, model ID, base URL and API key into a Workspace-level model configuration. Agents reference it through the model identifier; the server resolves it in the current Workspace and uses the corresponding credentials. Console supports create, list, edit, delete, probe and key-status inspection.

POST /v1/model_cards GET /v1/model_cards POST /v1/model_cards/probe POST /v1/model_cards/:id/probe

8.2 Model resolution priority

  1. The Agent-specified model matches a Model Card in the current Workspace.
  2. The Workspace default Model Card.
  3. Organization default model configuration, if enabled by the deployment.
  4. The server fallback ANTHROPIC_API_KEY configuration.
Production recommendationPut model credentials for each business Workspace into Model Cards instead of sharing one global fallback key across all Workspaces. This makes rotation, audit and future Workspace-level usage attribution easier.

8.3 Local Runtimes, ACP Bridge and Sandboxes

This section describes two execution paths that are easy to confuse:

Local Runtime / OMA BridgeRegisters an ACP-compatible Agent on a user or team machine into OMA and provides a local execution channel.ACP Proxy Agent; Session runs on the runtime-bound machine.
Sandbox WorkerClaims Environment work on an independent Linux node, creates/manages OpenShell sandbox, and reports status, results and heartbeats.Sandbox-backed Sessions such as Default / Strands / Deep Agents.

OMA Bridge setup (ACP Proxy path)

  1. On the machine that will run the local Agent, execute npx @openma/cli@beta bridge setup.
  2. Complete the OAuth/pairing flow. The CLI writes credentials to ~/.oma/bridge/ and can install a background daemon.
  3. The daemon scans ACP-compatible Agents on the machine $PATH and reports the runtime plus ACP agents to OMA.
  4. Confirm heartbeat in Console Local Runtimes, then create an ACP Proxy Agent bound to that runtime.

Common ACP Agents include claude-acp, codex-acp, openclaw and hermes. The actual list depends on the daemon’s current scan and ACP registry result. Use OMA_BRIDGE_DEBUG_ACP=1 for debugging and OMA_BRIDGE_ONPREM_RUNTIME=1 for On-Prem runtime mode.

Sandbox Worker (isolated sandbox path)

  1. Create or select an Environment in OMA.
  2. Mint a worker key for that Environment through POST /v1/environments/:environmentId/worker_keys.
  3. Deploy apps/sandbox-worker on the Linux sandbox node and set OMA_BASE_URL, OMA_ENVIRONMENT_ID, OMA_ENVIRONMENT_KEY and OMA_WORKER_NAME.
  4. Set runner/provider, for example OMA_WORKER_RUNNER=openshell and SANDBOX_PROVIDER=openshell, and configure image, policy and gateway.
  5. Start the worker. It polls work, acknowledges, heartbeats and reports result/failure. The Environment Detail page shows worker keys and startup hints.

9. Evaluations, integrations and advanced capabilities

9.1 Eval Runs

An Eval Run is a reproducible Agent evaluation batch: it uses a selected Agent and Environment, executes a set of tasks, collects complete Session trajectories and decides pass/fail through Reward rules. It is intended for Agent regression tests, model/prompt acceptance, tool-call validation and pre-release stability checks.

One-sentence model:A Session is one real conversation; an Eval Run is a batch of automated tests; a Task is one test scenario; a Trial is one independent execution of that scenario.

9.1.1 Core objects

ObjectMeaningExample
Eval RunOne evaluation batch bound to one Agent, one Environment and multiple Tasks.Validate four capabilities of a customer-service Agent.
TaskA test scenario with task ID, one or more messages, optional setup, timeout and Reward.Ask the Agent to use bash to output a fixed marker.
TrialOne independent run of a Task, with its own Session, event stream and trajectory.Run the same Task three times to observe stability.
TrajectoryThe complete evaluation trace saved after Trial completion, including messages, thinking/tool events, status, model calls and token usage.Used for review, scoring and later comparison.

Task vs Trial:A Task is “what to test”; a Trial is “one actual execution.” With trials: 3, one Task creates three independent Sessions and the final view can show pass counts such as 2/3.

9.1.2 How to use

For On-Premise, the recommended current path is to create Eval Runs through the API or the repository smoke-test scripts. Console is mainly for list view, status monitoring, Task/Trial expansion and trajectory/reward inspection.

POST /v1/evals/runs
x-api-key: <workspace-api-key>
content-type: application/json

{
  "agent_id": "agent_xxx",
  "environment_id": "env_xxx",
  "tasks": [{
    "id": "bash-check",
    "messages": ["Use bash to run: printf OMA_OK"],
    "trials": 1,
    "timeout_ms": 3600000,
    "reward": {
      "type": "verifiable",
      "scorer": "bashOutputMarker",
      "opts": { "marker": "OMA_OK" }
    }
  }]
}

Successful creation returns a run_id. Poll GET /v1/evals/runs/:id until the Run becomes completed or failed. The repository provides a shortcut script:

$env:OMA_API_URL = "http://localhost:8787"
$env:OMA_API_KEY = "oma_..."
$env:OMA_AGENT_ID = "agent_..."
$env:OMA_ENV_ID = "env_..."
node scripts/eval-smoke/run.mjs all

The API key automatically determines the current Workspace/Tenant; no extra tenant_id is required. The Environment must be ready, and the embedded worker or external sandbox-worker must be running normally.

9.1.3 Reward and pass judgment

A Reward scores one Trial result, usually normalized from 0 to 1. It is not model token cost and not the Agent’s own claim of success; it is the result of platform verifier/scorer logic over the trajectory.

Reward typePurposeTypical configuration
No RewardOnly verify the Session completed successfully.Pass when the Trial reaches idle with no error.
verifiableUse built-in scorers to inspect messages, tools or bash output.agentMessageContains, bashOutputMarker, fileWritten, toolUsed, idleNoError.
scriptRun a verification script inside the Trial sandbox; exit code 0 means pass.Run tests or inspect generated files.
compositeCombine multiple verifiers and calculate a weighted total score.Require both successful bash execution and output containing a target marker.

Console Pass rate is passed Trials divided by total Trials. Reward breakdown shows finer scoring reasons from the trajectory. Reward 0 does not necessarily mean the Session crashed; the Agent may have completed execution without satisfying the scoring condition.

9.1.4 On-Premise background execution model

POST Eval Run
main-node scheduler
Create independent Session
embedded / external worker
Collect trajectory
verifier / reward
Complete Run
  1. The API writes the initial Run and Task/Trial states to the main database.
  2. The main-node Eval Runner periodically scans pending/running Runs.
  3. Each Trial creates an independent Session and sends the Task’s first message; multiple messages are sent sequentially.
  4. The Session executes its Harness through the configured embedded or external execution plane.
  5. After the Session enters idle, the Runner reads events and full-status and builds a trajectory.
  6. The verifier scores according to the Reward configuration, updates Trial, Task and Run state, and saves the trajectory.
About duration:The default EVAL_TICK_CRON="* * * * *" advances once per minute. A model may finish quickly, but the Runner may wait until the next tick to discover idle, send the next message or complete scoring. Therefore roughly 1 to 2 minutes for a single-message Task, and one additional tick for a multi-message Task, are expected under the polling architecture and do not imply model latency. Test deployments may use EVAL_TICK_CRON="*/10 * * * * *" after weighing database and worker load.

9.1.6 Evaluation Plans, review gates and Temporal

Evaluation Plans organize reusable cases, references and revisions. A published Plan can run through the Temporal execution path, which exposes live case progress and preserves evidence for later review. Review gates can pause promotion until the required evidence or reviewer decision is available. Treat cases suggested by OMA as proposals: inspect prompts, fixtures and assertions before publishing.

Workflow Runs can be deleted only after reaching a terminal state; deletion also performs cascading cleanup. If a run is still active, cancel it and wait for the terminal status before retrying deletion.

9.4 Dreams and asynchronous jobs

Console visibilityThe current Console has no Dreams page. Dreams are an API/SDK capability provided by the On-Premise server.

What is a Dream:a background Memory curation job. It reads an existing Memory Store, optionally references several Sessions, calls a model to merge duplicate memories, clean outdated content and distill recurring patterns, then creates a new Curated Memory Store. It usually does not overwrite the original Memory Store directly.

Source Memory Store
Optional Session context
Model curation
New Memory Store
Future Agent use

Lifecycle:pending → running → completed / failed / canceled. The create API returns quickly and clients must query Dream status. After completion, read the curated result from outputs[].memory_store_id.

Input requirements:one Memory Store is required. Sessions are optional and must belong to the current Workspace. The current implementation mainly provides Session IDs and titles to the curator rather than full conversation transcripts, so Dreams currently rely primarily on Memory Store content.

Current limits:supported models are claude-opus-4-7 and claude-sonnet-4-6; a Dreams beta header is required; there is no Console usage/dashboard; Dreams are not a general-purpose task orchestrator.

10.3 API usage principles

  • All automation requests should carry the correct fixed Workspace context; do not rely on the user’s last Console selection.
  • Use separate API Keys for different business domains so revocation, rotation and caller tracing stay simple.
  • Do not commit API Keys to Git, write them to logs or place them in Memory.
  • For long-running tasks, prefer SSE or Session-status polling instead of repeatedly creating new Sessions at high frequency.

13. Troubleshooting

No Workspace after login

Confirm the user has created or joined a Workspace. Check browser cookies, PUBLIC_BASE_URL and whether the authentication database points to the expected instance.

Adding a member shows User account not found

Confirm the target user has signed in and exists in this On-Premise instance user directory. If OMA_ALLOWED_EMAIL_DOMAINS is set, confirm the email domain is on the system-wide allowlist. An identity existing in the IdP does not mean the local user table already has a record.

Agent cannot call the model

Check whether the Agent model ID matches a Workspace Model Card. Use Model Card probe. Confirm base URL, provider, key and network egress. If no Model Card exists, then check the server fallback ANTHROPIC_API_KEY.

Session stays rescheduled for a long time

Check whether the Environment is ready, Runtime is enrolled/heartbeat healthy, worker can claim work, and the external configuration required by SANDBOX_PROVIDER is present.

Memory is visible in Console but not synchronized in sandbox

In local mode, check MEMORY_BLOB_DIR, file permissions and watcher. In S3 mode, check all connection parameters, bucket prefix and poll interval, and confirm multi-instance deployments use shared object storage.

Live events do not refresh

Check the SSE connection, whether the reverse proxy allows long-lived connections, and whether API Key plus active tenant are correct. In PostgreSQL multi-instance scenarios, check event fanout dependencies.

Security incident handling

If an API Key or Vault credential leaks, revoke/rotate it immediately, inspect related Sessions, model calls and integration logs, then follow the enterprise incident response process. Do not only delete the display name in Console.

Workspace 是用户在 Console 中看到的工作区；服务端将它作为 Tenant 实现。Workspace 不是一个 UI 标签，而是资源和请求隔离的根边界。

5. Agent、Harness 与 ACP Proxy

Agent 是“如何工作”的可复用配置，不是一次执行。Harness 是 Agent 的执行引擎；ACP Proxy 是其中一种特殊执行方式，用于把 Agent loop 委派到已连接的本地 ACP runtime。

5.1 Harness Catalog

Console 的 /harnesses 页面是 Harness Catalog。它从 GET /v1/harnesses 读取当前部署可用的 manifest，展示名称、状态、provider、版本、是否已安装/启用、能力支持程度、原生工具、兼容性和 OMA 工具列表。

Harness定位适合场景状态

StrandsStrands Agents 支持的 Agent loop需要使用 Strands 运行方式的 Agentbeta
Deep Agents带规划、skills 和同步子 Agent 委派的高级 loop复杂分析、分解任务、多步规划beta

安全要求不要把 API token、密码或 OAuth refresh token 放进 Agent system prompt、Skill 文件、Memory 或普通 File。应使用 Vault，并在测试完成后撤销不再需要的凭据。

7.5 Skills 与 MCP

Skills 是可复用的提示片段和文件，支持上传、列表、版本和删除；MCP 入口支持连接探测和凭据匹配。Skill 适合稳定领域知识，Memory 适合会随任务变化的持久信息，Vault 适合秘密。

7.6 资源可见性与访问审核

资源可以按当前访问策略设为创建者私有，或对 Workspace 可见。Console 提供 Workspace 资源访问清单，并优先标出需要审核的资源。获得许可的成员可以创建私有 Agent、Skill 和 Memory Store；owner 与 admin 负责 Workspace 级可见性和权限策略。

Model Card 将 provider、model ID、base URL 和 API key 绑定为 Workspace 级模型配置。Agent 通过模型标识引用它；服务端按当前 Workspace 解析并使用对应凭据。Console 支持创建、列表、编辑、删除、探测和查看 key 状态。

8.2 模型解析优先级

  1. Agent 指定的模型与当前 Workspace Model Card 匹配。
  2. Workspace 默认 Model Card。
  3. 组织默认模型配置（如果部署启用）。

8.3 Local Runtimes、ACP Bridge 与 Sandboxes

组件作用对应 Harness / Session

9. 评估、集成与高级能力

9.1 Eval Runs

Eval Run 是一次可重复的 Agent 评估批次：它使用指定的 Agent 和 Environment，执行一组任务，收集完整 Session 轨迹，并根据 Reward 规则判断任务是否通过。它适合做 Agent 回归测试、模型/提示词变更验收、工具调用验证，以及上线前的稳定性检查。

一句话理解：Session 是一次实际对话；Eval Run 是一批自动化测试；Task 是其中一个测试场景；Trial 是该场景的一次独立执行。

9.1.1 核心对象

对象含义示例
Eval Run一次评估批次，绑定一个 Agent、一个 Environment 和多个 Task。验证客服 Agent 的 4 个能力。
Task一个测试场景，包含任务 ID、一个或多个 messages、可选 setup、timeout 和 Reward。要求 Agent 使用 bash 输出固定标记。
Trial一个 Task 的一次独立运行，拥有独立 Session、事件流和 trajectory。同一个 Task 执行 3 次以观察稳定性。
TrajectoryTrial 完成后保存的完整评估轨迹，包含消息、思考/工具事件、状态、模型调用和 token usage。用于复盘、评分和后续对比。

Task 与 Trial 的区别：Task 是“要测什么”，Trial 是“实际测了一次”。配置 trials: 3 后，一个 Task 会创建 3 个独立 Session，最终可看到通过次数，例如 2/3。

9.1.2 如何使用

On-Premise 当前建议通过 API 或仓库中的 smoke-test 脚本创建 Eval Run；Console 主要用于列表、状态监控、Task/Trial 展开和 trajectory/reward 查看。

POST /v1/evals/runs
x-api-key: <workspace-api-key>
content-type: application/json

{
  "agent_id": "agent_xxx",
  "environment_id": "env_xxx",

API key 自动决定当前 Workspace/Tenant，不需要额外传 tenant_id。Environment 必须处于 ready 状态，并且 embedded worker 或 external sandbox-worker 必须正常运行。

9.1.3 Reward 与通过判断

Reward 是对一个 Trial 的结果评分，通常归一化为 0 到 1。它不是模型 token 费用，也不是 Agent 自己声称的结果，而是平台根据 trajectory 执行 verifier/scorer 得出的结果。

Reward 类型用途典型配置
无 Reward只验证 Session 是否成功完成。Trial 正常 idle 且无错误即通过。
verifiable使用内置评分器检查消息、工具或 bash 输出。agentMessageContains、bashOutputMarker、fileWritten、toolUsed、idleNoError。
script在 Trial sandbox 中执行验证脚本，退出码为 0 代表通过。运行测试脚本或检查生成文件。
composite组合多个 verifier，并按权重计算总分。同时要求 bash 成功和输出包含目标标记。

Console 中的 Pass rate 是通过 Trial 数除以 Trial 总数；Reward breakdown 则显示 trajectory 中更细的评分原因。Reward 为 0 不一定表示 Session 崩溃，也可能表示 Agent 执行完成但没有满足评分条件。

9.1.4 On-Premise 后台执行原理

  1. API 将 Run 和 Task/Trial 初始状态写入主数据库。
  2. main-node 的 Eval Runner 定期扫描 pending/running Run。
  3. 每个 Trial 创建独立 Session，发送 Task 的第一条 message；多条 messages 会按顺序发送。

关于耗时：默认 EVAL_TICK_CRON="* * * * *" 每分钟推进一次。模型可能很快完成，但 Runner 可能需要等待下一次 tick 才能发现 idle、发送下一条 message 或完成评分。因此单消息 Task 出现约 1 至 2 分钟、多消息 Task 多一个 tick 的等待是当前轮询架构的预期行为，不等同于模型性能问题。测试环境可配置 EVAL_TICK_CRON="*/10 * * * * *"，生产环境需要根据数据库和 worker 负载权衡。

13. 常见问题与排障

登录后没有 Workspace

确认用户已创建或被加入 Workspace；检查浏览器 Cookie、PUBLIC_BASE_URL 和认证数据库是否指向预期实例。

添加成员显示 User account not found

确认目标用户已登录并存在于当前 On-Premise 实例的用户目录中。如果设置了 OMA_ALLOWED_EMAIL_DOMAINS，还要确认邮箱域名在系统级白名单中。SSO 身份在 IdP 中存在，不代表本地用户表已经有记录。

Agent 无法调用模型

检查 Agent 的 model ID 是否与 Workspace Model Card 匹配；使用 Model Card probe；确认 base URL、provider、key 和网络出口。若没有 Model Card，再检查服务端回退 ANTHROPIC_API_KEY。

Session 长时间 rescheduled

检查 Environment 是否 ready、Runtime 是否 enrolled/heartbeat 正常、worker 是否能够领取 work，以及 SANDBOX_PROVIDER 所需的外部配置。

Memory 在 Console 看得到但沙箱不同步

本地模式检查 MEMORY_BLOB_DIR、文件权限和 watcher；S3 模式检查所有连接参数、bucket 前缀和 poll interval，并确认多实例使用共享对象存储。

实时事件没有刷新

检查 SSE 连接、反向代理是否允许长连接、API Key 与 active tenant 是否正确；PostgreSQL 多实例场景检查事件 fanout 依赖。

安全事件处理

API Key 或 Vault 凭据泄露时立即 revoke/rotate，检查相关 Session、模型调用和集成日志，再按企业事件响应流程处理。不要只删除 Console 中的显示名称。
