OPERATIONS · RECOVERY

Agent Operations

A guided example of inspecting execution evidence, recovering a Session after interruption, and updating an Agent while preserving the version snapshot already in use.

Illustrative guided simulation. This page describes a product scenario using synthetic demo data. It does not connect to a live Slack workspace, Open Atlas service, MCP endpoint, customer environment, or OMA deployment.

THE FLOW

How the story unfolds.

01

Inspect the Session

An operator opens the event history to review user input, model activity, tool calls, results, and status transitions.

02

Handle interruption

The run is interrupted or the worker becomes unavailable. The Session returns to an idle, inspectable state with its prior events retained.

03

Continue deliberately

An authorized user sends the next instruction to continue work. OMA rebuilds context from the persisted Session history.

04

Publish an update

The operator publishes a new Agent version. Existing Sessions retain the version snapshot they were created with.

What this illustrates

  • The append-only event history supports operational review and recovery after a failed or interrupted run.
  • A Session uses its pinned Agent configuration; publishing a new Agent version does not rewrite that Session’s snapshot.
  • Recovery is an explicit managed lifecycle, not a claim that every in-flight external side effect can be rolled back.

Operator considerations

  • Review tool results and external side effects before resuming an interrupted task.
  • Use permissions and tool confirmation policies appropriate to the actions an Agent can take.
  • Validate the new Agent version in a controlled Session before adopting it for production work.
